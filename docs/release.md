# Local Release Process (Make + Nix + GitHub Releases)

Releases run from an operator machine, not GitHub Actions. One command creates
and pushes the Git tag, builds the ISO plus Linux/macOS `kctl` binaries,
packages `dist/`, then creates or updates the GitHub Release assets.

## Version sources (policy)

| Source | Role |
|--------|------|
| [`VERSION`](../VERSION) (single line, e.g. `0.2.0`) | **Product / packaging version**: Nix `kcoreVersion`, ISO filename `kcoreos-$(VERSION)-x86_64-linux.iso`, Git tag `v$(VERSION)`, release assets. **Bump this for every release.** |
| `crates/*/Cargo.toml` `version = "…"` | Rust crate semver. **Not automatically tied to `VERSION`.** This repo usually bumps crate versions in the same PR as `VERSION` so `kctl --version` matches the product version. |

## Preconditions

- The version bump PR is merged to `main`, including [`VERSION`](../VERSION)
  (and crate versions, when applicable).
- Run on Linux **x86_64** with Nix/flakes working. The release flow builds
  Linux `kctl` with Nix and cross-compiles Intel macOS / Apple Silicon `kctl`
  with `cargo-zigbuild` from the Nix dev shell.
- `gh` is available and authenticated from the Nix dev shell. Use
  `nix develop --command gh auth status` to verify, or set `GH_TOKEN` for
  non-interactive use. If a local `.env` exists, `scripts/release.sh publish`
  sources it before invoking `gh`, so `GH_TOKEN=...` in `.env` is enough for
  `make release`.
- `cosign` signs `dist/SHA256SUMS` during the publish step, using Sigstore
  keyless signing. This opens a **browser window for OIDC login**, so
  `make release` is not fully unattended. Choose GitHub and sign in as
  `82217+rtacconi@users.noreply.github.com`. The step checks the bundle
  against that identity and stops if another account signed it. A maintainer without `cosign`
  configured must opt out explicitly with `RELEASE_FLAGS=--no-sign`; the
  release is then unsigned and
  [`scripts/verify-release.sh`](../scripts/verify-release.sh) will reject it.
  See [release-verification.md](./release-verification.md).
- The working tree is clean before `make release`; the script tags the exact
  checked-out commit.

## Steps

1. **Bump version**  
   Edit [`VERSION`](../VERSION) to `X.Y.Z` (and optionally align `crates/kctl/Cargo.toml` and other crates if you follow the policy above). Open a PR, get CI green, merge to `main`.

2. **Run the local release**

   ```bash
   git fetch origin main && git checkout main && git pull
   make release
   ```

   `make release` runs [`scripts/release.sh`](../scripts/release.sh) `release`:

   - validates `VERSION`,
   - creates annotated tag `v$(cat VERSION)` if missing,
   - verifies an existing local or remote tag points at the current commit,
   - pushes the tag to `origin`,
   - builds the ISO and Linux `kctl` with Nix,
   - cross-compiles `kctl` for Intel macOS and Apple Silicon,
   - packages `dist/` and generates both SBOMs,
   - signs `dist/SHA256SUMS` with `cosign`,
   - creates the GitHub Release through `gh api`,
   - uploads release assets one by one with `gh release upload --clobber`.

3. **Verify what you published**

   ```bash
   make verify-release V=v$(cat VERSION)
   ```

   See the post-release checklist below.

## Individual targets

```bash
make release-tag
make release-build
make release-dist
make release-sign
make release-publish
```

`RELEASE_FLAGS` is passed through to `scripts/release.sh`, e.g.
`make release RELEASE_FLAGS=--no-sign`.

The release packaging step produces:

- `dist/kctl-$(VERSION)-linux-x86_64.tar.gz` (binary at archive root: `kctl`)
- `dist/kctl-$(VERSION)-macos-x86_64.tar.gz` (Intel macOS binary at archive root: `kctl`)
- `dist/kctl-$(VERSION)-macos-aarch64.tar.gz` (Apple Silicon binary at archive root: `kctl`)
- `dist/kcoreos-$(VERSION)-x86_64-linux.iso` (release asset name; copied from the single ISO produced under `result-iso/iso/`)
- `dist/kcore-$(VERSION)-crates.cdx.json` (CycloneDX SBOM of the Rust dependency graph)
- `dist/kcore-$(VERSION)-iso-closure.cdx.json` and `.spdx.json` (the ISO's Nix closure, both formats)
- `dist/kcore-$(VERSION)-release.json` (the version contract: commit, schema, tested OS pins, docs URL, Terraform provider coordinate)
- `dist/SHA256SUMS` for all assets
- `dist/SHA256SUMS.sigstore.json` from the publish step (absent under `--no-sign`)

SBOMs are generated by [`scripts/sbom.sh`](../scripts/sbom.sh), which
`release-dist` runs before writing `SHA256SUMS` so they are covered by it.
They can be built on their own with `make sbom` (crates, seconds) and
`make sbom-iso` (ISO closure; needs the ISO built first). Neither is
committed, so nothing about them runs in pull-request CI.

## Post-release checklist

1. **Verify the published release the way an auditor would.** This is the
   only real test of the signature, because it exercises the download,
   `cosign verify-blob` and `sha256sum` path end to end against GitHub:

   ```bash
   make verify-release V=vX.Y.Z
   ```

   If this is the **first signed release**, verification has no published
   identity to check against yet. Run it once with the identity you signed
   as, then record that value in
   [release-verification.md](./release-verification.md) and in the
   `SIGNER_IDENTITY` / `DEFAULT_SIGNER_IDENTITY` defaults of
   `scripts/verify-release.sh` and `scripts/get-kctl.sh`:

   ```bash
   KCORE_SIGNER_IDENTITY='you@example.org' make verify-release V=vX.Y.Z
   ```

2. **Check the release page** lists the ISO, the three `kctl` archives, both SBOMs, `kcore-$(VERSION)-release.json`, and `SHA256SUMS.sigstore.json`.

3. **Spot-check an SBOM.** `make sbom` is fast and deterministic enough that a
   mismatch means something went wrong in packaging rather than in the tool.

`make verify-release` is deliberately **not** part of pull-request CI: it
needs a published release to exist and depends on network access to Rekor,
which is exactly the kind of check that fails for reasons unrelated to the
change under review.

By default publishing uses GitHub-generated release notes unless `RELEASE_NOTES.md`
exists. To force custom notes:

```bash
RELEASE_NOTES=path/to/notes.md GH_TOKEN=... make release-publish
```

## What one version ships

`VERSION` names the ISO, the git tag, the docs tree, and the Terraform provider. `dist/kcore-$(VERSION)-release.json` is the contract those artifacts copy. The tag is what an operator installs:

```bash
kctl update version set vX.Y.Z
```

The controller resolves the tag to its commit, reads `lib.kcore` from that commit's flake (version and schema), and rolls every node that runs another version to it, one node at a time. A lower tag is a downgrade. Each node writes the tag's host flake (`nix/host-flake.nix`, with `inputs.kcore.url = "github:kcorehypervisor/kcore/vX.Y.Z"`) and lets `nix` lock it, so its `/etc/nixos/flake.nix` and `flake.lock` match what the vX.Y.Z ISO installs. On the Community Edition the build compiles the Rust packages on the node. Nixpkgs still comes from `cache.nixos.org`.

The ISO built from the tag checkout ships that flake and its lock, so an air-gapped install needs no network. Tag updates on an air-gapped site resolve against a mirror: `kctl update version set vX.Y.Z --flake-ref git+https://mirror.example/kcore`.

A later private channel will serve prebuilt closures of newer versions, plus the kcore provisioner and the backup service. That channel is not part of this Community release. Community nodes keep compiling the public git commit.

After the GitHub Release is up:

1. Snapshot the operator docs for this version and deploy the site. From the `kcore-site` repository:

   ```bash
   ./scripts/snapshot-docs.sh X.Y.Z <schemaVersion>
   ```

   `/docs/user/` stays the latest stable pages. `/docs/X.Y.Z/` is the frozen copy. The schema version is `SCHEMA_VERSION` in `crates/controller/src/db.rs`.

2. Cut `terraform-provider-kcore` at the same `X.Y.Z`. The `kcore_slurm_cluster` resource is cut with the same `VERSION`. Its cluster version resource takes the release tag and calls `SetClusterVersion`; changing the tag starts the upgrade or downgrade. Publish it to the Terraform Registry.

3. `make verify-release` checks the signature. It does not deploy the site or the provider.

## Artifact notes

- **Linux kctl** is the **Nix-built** `kctl` from `.#kctl` (same lineage as the ISO), not a raw `cargo build`.
- **macOS kctl** is cross-compiled with `cargo zigbuild` for `x86_64-apple-darwin` and `aarch64-apple-darwin`.
- **Platforms**: Linux x86_64 (glibc via Nix), Intel macOS, and Apple Silicon macOS. No musl/static Linux build in this flow.
- **Large files**: ISOs are ~1–2 GiB; GitHub per-file limit is 2 GiB. Stay under that or split hosting for huge artifacts.

## Troubleshooting

- **Tag already exists on a different commit**: the script stops rather than moving a release tag. Check out the tagged commit or intentionally delete/recreate the tag yourself.
- **`gh release create` fails on `--verify-tag`**: run `make release-tag` first, or check that the remote tag exists: `git ls-remote origin refs/tags/vX.Y.Z`.
- **Wrong ISO name**: Nix may place the built ISO under a NixOS-derived name in `result-iso/iso/`; the dist step discovers the single `*.iso` there and copies it to the release asset name `kcoreos-$(VERSION)-x86_64-linux.iso`.
- **Publish authentication**: run `nix develop --command gh auth status`, or set `GH_TOKEN` in the environment / local `.env` for non-interactive `gh`. A classic token with `repo` scope works; fine-grained PATs need release-capable repository permissions (`Contents: Read and write`, and in some cases `Workflows: Read and write`).
- **Large ISO uploads**: `scripts/release.sh publish` intentionally creates the release record first and uploads assets separately, because an all-in-one `gh release create ... <large ISO>` can sit for a long time with no useful progress output.

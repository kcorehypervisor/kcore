What kcore does

A failed host update boots the previous generation. Windows guests run. The evaluation ISO is free.

Read this first

  • A failed host update boots the previous generation.
  • Windows Server and Windows desktop guests run.
  • One physical GPU can be assigned to one VM. NVIDIA vGPU, many VMs on one card, is not available.
  • Live migration needs shared Ceph storage. Control-plane replication across datacenters is not vSphere HA.
  • kcore-migrate inventories vCenter or Proxmox and converts exported disks to qcow2 or raw. It does not read disks straight from vCenter. Cutover is a project. See the import guide and kcore-migrate.
  • Price is per CPU socket per year. The evaluation ISO is free. Download it from GitHub Releases.

Bare-metal install

A provisioner configures servers over IPMI and Redfish. It netboots kcore with UEFI HTTP boot.

A failed update boots the previous generation

Host updates are one transaction. If an update fails, the machine boots the previous generation.

  • ✓
    Immutable Base System
    The host OS is read-only. Configuration lives in Nix, not scattered across /etc.
  • ✓
    Boot into Previous Generation
    Every NixOS generation is kept. Select a previous one at boot or switch remotely.
  • ✓
    Download the ISO
    Official ISOs are produced from flake.nix. Download the evaluation ISO. You do not build it.

Infrastructure as Code

VMs are resources in Terraform. You write HCL, run terraform apply, and the provider talks to the kcore API over gRPC. Standard workflow, no special tooling.

  • 📝
    Real Terraform Provider
    Written in Go using the Terraform Plugin SDK. Not a shell wrapper.
  • 🔄
    Git-friendly
    HCL and YAML are text files. Diff them, review them, track changes over time.
  • 📊
    Desired State
    The controller stores desired state. Node agents reconcile. Standard controller pattern. 
# Provider kcorehypervisor/kcore 0.5.0
resource "kcore_vm" "web" {
  name               = "web"
  cpu                = 2
  memory_bytes       = 4294967296
  storage_backend    = "filesystem"
  storage_size_bytes = 53687091200
  image_url          = "https://example.com/debian.qcow2"
  image_sha256       = "<sha256>"

  nic {
    network = "production"
  }
}

resource "kcore_vm" "db" {
  name               = "db"
  cpu                = 4
  memory_bytes       = 8589934592
  storage_backend    = "lvm"
  storage_size_bytes = 214748364800
  image_url          = "https://example.com/debian.qcow2"
  image_sha256       = "<sha256>"

  nic {
    network = "production"
  }
}

AI Agent Integration

kcore includes an MCP (Model Context Protocol) server. Any MCP-compatible AI agent can list nodes, create VMs, check status, and generate Terraform configs through it.

  • 🤖
    MCP Server
    Runs alongside the controller. Exposes tools for VM and node management over MCP.
  • 💡
    Terraform Output
    Agents generate HCL you can read and modify. No black-box deployments.
  • 📈
    Query Infrastructure
    Agents can check VM status, node health, and resource usage to help you troubleshoot.

Complete features

In the product as of kcore 0.6.1. Work that is still planned stays on the roadmap.

Virtual machines

  • Create, update, start, stop, and delete. YAML and Terraform.
  • Cloud-init, SSH keys, labels, and a wait for boot or SSH.
  • Windows Server and Windows desktop guests.
  • Serial console in the browser and from kctl console.
  • One physical GPU passed through to one VM.
  • NVIDIA vGPU slices. The host needs an AI Enterprise vGPU manager package.
  • NAT, bridge, and VXLAN networks, extra NICs, IPv6, and VLANs.
  • Security groups, DNAT, and an east-west filter on a bridge.
  • Live and cold migration on Ceph, LVM, and ZFS. A filesystem disk stays put.
  • Ceph VMs restart on another node after a missed heartbeat.

Containers and ingress

  • OCI containers on containerd, beside VMs, on one workload API.
  • Ingress on Caddy with Coraza, automatic certificates, and a keepalived VIP.
  • Routes to a VM, an external address, or a Kubernetes Service.
  • WAF detect and block, rate limits, and IP allow and deny lists.

Storage

  • Filesystem, LVM, ZFS, and Ceph RBD volumes, including resize.
  • Snapshots, schedules, clone, restore, and flatten on Ceph, ZFS, and LVM.
  • New Ceph clusters encrypt OSD disks. An RBD volume can be LUKS-encrypted.
  • Ceph RBD volumes for VM disks, replicated across nodes.
  • Declarative disk layouts from the installer through day-2.
  • Changed-block export and import for a backup tool.
  • kcore Vault: retain-until backups, a ZFS repository, and S3 Object Lock.

Cluster and host services

  • mTLS, RBAC, an audit log, certificate rotation, CRL, and OCSP.
  • Dashboard sign-in with a password and TOTP.
  • Multi-controller replication, including across datacenters.
  • Scheduler: most free memory, required labels, anti-affinity, overcommit.
  • ISO install, kcore-infect, approve, cordon, drain, and delete.
  • Host update as one transaction. A failed boot uses the previous generation.
  • IPMI and Redfish provisioner, UEFI HTTP boot, PowerDNS, and Kea.
  • Appliance console on the node.
  • node_exporter and VictoriaMetrics.
  • Webhooks, an MCP server, and the Terraform provider.
  • PostgreSQL on the node, one database per node.
  • Kubernetes on kcoreOS with Cilium.
  • Slurm on kcoreOS. Compute nodes are left to slurmd.
  • kcore-migrate inventories vCenter or Proxmox and converts exported disks.

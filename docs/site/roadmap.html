☑ Core Platform

End-to-end declarative VM lifecycle on bare metal. Controller, node agent, CLI, networking, storage, mTLS — all working in production.

VM Lifecycle

  • Create, delete, start, stop, update VMs
  • Container workloads via containerd (kctl workload / kctl container)
  • Unified workload API for VMs and containers
  • Desired-state reconciliation via Nix
  • Cloud Hypervisor runtime
  • YAML manifest support (kctl create vm -f)
  • Wait for boot / SSH readiness
  • Windows Server and Windows desktop guests
  • Serial console (kctl console and the dashboard)
  • One physical GPU assigned to one VM

Storage & Volumes

  • Filesystem, LVM, and ZFS backends
  • Volume create, delete, attach, detach
  • Per-VM storage provisioning on create
  • Storage overview API (dashboard)

Networking

  • NAT, bridge, and VXLAN network types
  • Cross-host VXLAN with optional outbound NAT
  • VLAN ID support on gateway
  • Security groups with ingress + optional DNAT policy
  • kctl apply -f ... kind-based manifest dispatch (kubectl-style)
  • dnsmasq + nftables per network

Security & Operations

  • Full mTLS PKI (CA, sub-CA, per-node certs)
  • CN-based gRPC authorization
  • Cert rotation (kctl rotate)
  • Node drain and approval flow
  • Compliance reporting

Node Bootstrap

  • Automated node install via kctl node install
  • NixOS ISO with disko integration
  • PKI bootstrap into /etc/kcore/certs
  • Multi-disk layout (OS + data disks)

Platform

  • Capacity-aware scheduler (most-free-first)
  • Image management (URL+SHA256, upload, pull)
  • SSH key management
  • Dashboard (web UI), with password and TOTP sign-in
  • Terraform provider (separate repo)
  • MCP server for agents, calling the same API
  • Host updates as one transaction (ClusterUpdate). A failed boot returns to the previous generation
  • kcore-infect installs kcoreOS on an existing systemd Linux host

⚙ Declarative Disk Partitioning

Declarative disk layouts from install through day-2. The live ISO generates disko-config.nix and runs disko --mode format,mount; the kcore.disko NixOS module expresses OS and data disks with optional merged fragments; nodes default to installer-only ownership and can be moved to controller-managed for declarative DiskLayout resources. The controller stores DiskLayout objects in its replicated DB and reconciles them to the target node, which atomically persists the layout to /etc/kcore/disk/current.nix and chains nixos-rebuild test + switch. The node-agent classifier refuses any layout that would touch a disk currently backing an active kcore volume, LVM PV, or ZFS pool member — the controller never touches VMs.

  • Shipped Install-time disko: generates disko-config.nix, runs disko --mode format,mount
  • Shipped modules/kcore-disko.nix with kcore.disko.* (including managementMode, controllerFragments, and persistedLayoutPath)
  • Shipped Ownership split: /etc/kcore/disk-management-mode — default installer-only; controller-managed unlocks declarative apply (legacy disko-management-mode path read as fallback)
  • Shipped Per-node kctl node apply-disk -f … [--apply] [--no-rebuild] → node-agent ApplyDiskLayout: classifier-gated, atomic persist to /etc/kcore/disk/current.nix, automatic nixos-rebuild chain
  • Shipped Declarative fleet rollout: kind: DiskLayout resource, controller CRUD + replication outbox, controller-side reconciler tick that pushes unobserved generations to nodes and writes back observed_generation + phase
  • Shipped Safe / dangerous classifier in kcore-disko-types shared crate (used by both controller pre-flight and node-agent authoritative gate); refusal codes surface on status.refusalReason

🔬 Property-Based Testing & Bounded Model Checking

The remaining three phases of the formal-methods plan landed alongside TLA+: generative property tests across every Rust crate, Kani bounded proofs on the security-critical sanitisers, and proptest coverage of database CRUD invariants. All four phases (proptest, Kani, DB invariants, TLA+) are now required CI gates.

  • Shipped proptest on Nix generation: escape round-trip, attribute-key sanitisation, structural validity (controller, node-agent, kctl, dashboard)
  • Shipped Kani harnesses for path traversal, NUL injection, segment validation, and Nix string escaping in the dedicated kcore-sanitize leaf crate (zero non-std deps, so proofs compile in seconds)
  • Shipped Kani harnesses on the DiskLayout diff parser in kcore-disko-types: extract_target_devices never panics, comment stripper preserves length, every emitted path is /dev/-prefixed, extraction is deterministic
  • Shipped Per-harness CI matrix — each #[kani::proof] runs on its own GitHub Actions runner with shared toolchain cache, completing the gate in ~1–2 min on warm cache
  • Shipped proptest on database CRUD invariants: VM, node, network, security-group, SSH-key, and DiskLayout round-trips, idempotent upserts, foreign-key integrity, cascading delete, and the reconciler queue (list_disk_layouts_needing_reconcile)
  • Shipped proptest fuzzers for the DiskLayout safe/dangerous classifier: safe verdicts never overlap an active-VM, system-mount, LVM PV, or zpool-member device; classifier is deterministic on identical inputs
  • Shipped 575 workspace tests (incl. proptest fuzzers) + Kani matrix + TLA+ trace bridge run on every pull request
August 2026 — Shipped

💻 Dashboard Web Console

In-browser serial console in the dashboard for datacenter use: a CLI terminal for day-to-day work, rescue, and installers. Also available from the CLI via kctl console. Console opens are recorded in the append-only audit log (actor, VM, timestamp). If you need a graphical desktop, install a VNC server (or equivalent) inside the guest OS yourself and reach it over the network. kcore does not provide a hypervisor-level graphical console — that would add complexity we do not need for headless workloads.

  • Shipped Serial / CLI console in the browser (xterm.js) via WebSocket to the node-agent serial endpoint
  • Shipped “Console” action on each VM in the dashboard, with paste, resize, and disconnect
  • Shipped mTLS-authenticated proxy through the dashboard — same trust model as the rest of the UI
  • Shipped kctl console <vm> for operator serial access from a terminal
  • Shipped Session audit: who opened which console, and when
September 2026 — Shipped

🔒 Security & Compliance

RBAC, audit logging, certificate lifecycle, SBOM export, and per-identity gRPC rate limiting. Node certificates rotate on their own, and revoked certificates are published over CRL and OCSP — see certificates & encryption. kctl get crypto-config reports the cryptographic posture. kctl get sbom exports the CycloneDX document, and release artifacts are signed with Sigstore.

  • Shipped RBAC roles: read-only, vm-admin, cluster-admin (per-operator certs CN=kctl:<name>, kctl operator)
  • Shipped Append-only audit log with actor, action, resource, timestamp (includes console session opens)
  • Shipped ListAuditEvents API (+ kctl audit / dashboard)
  • Shipped Console session audit: AttachVmConsole records who opened which VM console, and when
  • Shipped Automated certificate rotation and CRL/OCSP revocation — nodes generate their own keys and CSRs so private keys never leave the node, the sub-CA publishes a signed CRL and answers OCSP, and revoked peers are rejected on every RPC (kctl rotate node-certs, kctl revoke cert, kctl get pki-status)
  • Shipped SBOM generation and signed release artifacts — CycloneDX SBOMs in the GitHub release, SHA256SUMS signed with Sigstore keyless signing
  • Shipped New APIs: GetCryptoConfig, ExportSbom (kctl get crypto-config, kctl get sbom)
  • Shipped gRPC rate limiting — per-identity token bucket on the controller and node-agent (default 100 req/s, burst 200)
September 2026 — Shipped

💾 kcore SAN (Ceph)

Distributed shared block storage for the cluster — a vSAN-class fabric powered by Ceph on NixOS, with the controller filling the gaps NixOS does not declare. Replicated VM disks, cold drain without copying disks, and Cloud Hypervisor live migration over shared RBD all work today. See kcore SAN docs.

  • Shipped Declarative CephCluster resource (MON / MGR / OSD) with dedicated Ceph network
  • Shipped NixOS services.ceph + controller-owned bootstrap (keys, ceph-volume, health)
  • Shipped RBD storage backend for VMs (--storage-backend ceph)
  • Shipped Cold migrate / drain without copying disks (shared RBD)
  • Shipped Cloud Hypervisor live migration over shared RBD
  • Shipped Volumes: create, attach, detach, resize, snapshot, restore, and flatten
  • Shipped New clusters encrypt OSD disks (encryptOsds, immutable after create)
  • In Progress CephFS (SharedFilesystem) and S3 via RGW (ObjectStore, ObjectUser) are in the API. MDS and RGW lab automation is still incomplete, and VM virtio-fs is not in yet

📊 Advanced Scheduler

Topology-aware placement beyond most-free-first. The controller still spreads a new VM onto the ready node with the most free memory, then CPU. Free capacity is live heartbeat load subtracted from physical capacity times the overcommit ratio in controller.yaml.

  • Shipped Label-based affinity (--label dc=dc-a)
  • Shipped Anti-affinity rules for HA workloads
  • Shipped Overcommit ratio and load-aware placement

🌐 Networking Improvements

A VM can join more than one network. A network can add an IPv6 /64 beside IPv4, drop VM-to-VM traffic on its bridge, and reuse VXLAN addresses after a guest is deleted. Security groups still control north-south exposure, and named target-IP rules stay open when the east-west filter is on.

  • Shipped Multi-NIC / multi-homed VMs
  • Shipped IPv6 support
  • Shipped East-west firewall between VMs on the same bridge
  • Shipped Security groups with YAML apply flow and nftables rendering on nodes
  • Shipped VXLAN IP reclamation and improved peer discovery

💾 Volume snapshots and local-disk migration

Day-2 disks beyond the first Ceph fabric. Snapshots cover Ceph RBD, ZFS, and LVM. A filesystem disk is not snapshotted. LVM and ZFS guests can move while they run; a filesystem disk stays on its node.

  • Shipped Snapshot, clone, restore, and flatten for Ceph RBD, ZFS, and LVM. SnapshotPolicy prunes on a schedule
  • Shipped Changed-block export and import (ListVolumeChangedExtents, ReadVolumeBlocks, WriteVolumeBlocks) for an external backup tool
  • Shipped LUKS on an RBD volume (kctl encrypt volume)
  • Shipped Live migration of LVM and ZFS disks: a device-mapper mirror resyncs, then Cloud Hypervisor sends memory. Cold copy remains the fallback

🎮 GPU

One physical GPU can be assigned to one VM. NVIDIA vGPU slices a card across guests. The slice needs an NVIDIA AI Enterprise vGPU manager package on the host. Live migration does not move a passed-through device.

  • Shipped PCI passthrough (--pci). One card, one VM
  • Shipped NVIDIA vGPU host and slices (NodeVgpu, kctl node vgpu enable)
  • In Progress Intel and AMD SR-IOV slices use the same manifest. They have not been run on lab hardware

🔗 Ingress gateway

North-south HTTPS terminates on the cluster. Caddy presents the certificate, Coraza inspects the request, and keepalived holds the VIP. A route can target a VM, an external address, or a Kubernetes Service.

  • Shipped IngressGateway, IngressRoute, and WafPolicy from kctl, the dashboard, MCP, and Terraform
  • Shipped ACME (including DNS-01 and wildcards), TCP and SNI routes, rate limits, IP allow and deny lists
  • Shipped WAF detect and block modes, with ingress.waf.* webhooks and Caddy metrics in VictoriaMetrics
  • Planned Container backends, a Gateway API HTTPRoute, and certificates issued by the kcore PKI

🖥 Slurm on kcoreOS

Slurm runs on the nodes, not inside a guest. Compute members are cordoned, so the VM scheduler leaves them to slurmd. A node belongs to one Slurm cluster.

  • Shipped SlurmCluster: controller, optional backup controller, login, accounting (slurmdbd and MariaDB), and compute
  • Shipped kctl slurm plan, then apply. The dashboard, MCP, and Terraform provider cover the same resource

🖥 Bare-Metal

  • Shipped PostgreSQL from the NixOS services.postgresql package. One database per node (kind: PostgreSQL)

  • Planned MySQL from the NixOS package, declared and applied on the node the same way
  • Planned ClickHouse as a host service. Design only: no module or API yet

💾 Immutable backups

kcore Vault is a separate appliance. It snapshots the guest disks, pulls the changed blocks, and stores chunks that cannot be deleted before retain_until. kctl backup is still only a copy of the controller database.

  • Shipped Vault 0.1.1: policies, jobs, restore, and a browser console with TOTP
  • Shipped Immutability: appliance-enforced retention on the ZFS repository, and S3 Object Lock in COMPLIANCE mode
  • Shipped Incremental backups from changed extents. A restore writes the volume back as Ceph, LVM, or ZFS
October 2026 — Shipped

🛠 Operations & Node Lifecycle

Day-2 tooling for node removal, cluster health, a copy of the controller database, and moving shared-disk VMs when a node stops heartbeating.

  • Shipped GetClusterHealth API — kctl get cluster-health reports ready nodes, VMs left on not-ready nodes, certificates inside 30 days, and unresolved replication conflicts
  • Shipped Controller database copy — kctl backup -o snapshot.sqlite and kctl restore controller -f snapshot.sqlite --confirm. This is not guest backup.
  • Shipped Automatic VM migration on node failure — after 90 seconds without a heartbeat, Ceph VMs move to another healthy member; local-disk VMs stay on the failed node
  • Shipped Node cordon and certificate invalidation on delete — kctl node cordon stops new placement without moving VMs; kctl node delete refuses while VMs, workloads, or networks remain, then revokes the node's certificates (RFC 5280 reason 5) and removes the row
  • Shipped Bare-metal provisioner. It configures servers over IPMI and Redfish, and netboots kcore with UEFI HTTP boot.

Explicitly not planned

  • CSR approval flow (Kubernetes-style certificate signing requests)
  • Admission webhooks
  • Formal API versioning contract

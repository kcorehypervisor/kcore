# Slurm clusters

kcoreOS runs Slurm as host services on disjoint nodes. A `SlurmCluster` names
one controller, optional backup controller, optional login nodes, optional
accounting node, and one or more compute nodes. A node belongs to at most one
Slurm cluster.

Compute members are **cordoned**: the VM scheduler leaves them to `slurmd`.
Plan refuses a compute node that still hosts guest VMs. The controller, login,
and dbd roles may share a node with guests.

## Apply a cluster

```bash
kctl slurm plan -f hpc-a.yaml
kctl apply -f hpc-a.yaml
kctl get slurm-cluster hpc-a
```

`plan` returns `create`, `update`, `unchanged`, or `replace`. `replace` means an
immutable field changed (`metadata.name`, `clusterName`, or
`controller.nodeId`); delete the cluster and create it again.

The reconciler applies members in order `dbd`, `controller` (backup after
primary), `compute`, `login`. It waits for each NixOS rebuild and then polls
`sinfo` on the controller.

## NFS is a single point of failure

With `storage.mode: nfs` (the default), the controller node exports `/home` and
`/scratch` and every other member mounts them. If the controller is down, every
member loses those paths. Use `mode: none` if you do not need shared storage.

`storage.mode: shared-filesystem` is refused for now: the CephFS client key path
is still a scaffold, and kcore will not write a mount that cannot boot.

## Version skew

Slurm requires the database daemon to be at least as new as the controller, and
the controller at least as new as `slurmd`. Members of one Slurm cluster must be
in the same cluster-update run. The update reconciler orders `dbd`, controller,
compute, login and drains each compute node before its rebuild.

## Compute nodes are cordoned

Creating or updating a cluster cordons every compute member. `kctl delete
slurm-cluster` disables Slurm on the members, waits for the units to stop,
uncordons compute members, then drops the rows. `force` drops rows even when a
member is unreachable and does not pretend the units were removed.

Manual operations:

```bash
kctl slurm drain-node hpc-a node-108 --reason maintenance
kctl slurm resume-node hpc-a node-108
kctl slurm rotate-munge-key hpc-a
```

The munge key and slurmdbd password are generated by the controller, written
outside the Nix store, and never returned by Get.

## GPU jobs

`compute[].gres` is `none` (default) or `auto`. `auto` renders `gres.conf` from
the controller's GPU inventory. The host NVIDIA driver is off by default; set
`gpuDriver: true` only after deciding that the driver can be built on the node.
Licensing and build-on-node cost are yours. When the driver is off, `gres: auto`
plan-fails instead of writing a config that cannot start.

## Lab apply has not been run

This resource has not been applied to the live lab. The one-cluster lab apply
would rebuild NixOS on live hypervisors. Before that can happen the operator
must answer:

1. Which node is the first controller/login node, and which nodes become
   compute? The kcore controller host stays out unless you say otherwise.
2. Static management addresses and interface names for those nodes.
3. May those compute nodes be cordoned and emptied of guests before apply?
4. Which path or device on the controller node backs `/home` and `/scratch`?
5. First user accounts: name, uid, SSH public key.

No node was cordoned, drained, or rebuilt while this resource was added.
